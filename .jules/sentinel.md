## 2025-03-27 - [Fix Command Injection Risk in spawnProcess]
**Vulnerability:** The `spawnProcess` utility in `src/verify/formal.ts` explicitly enabled `shell: process.platform === "win32"` when spawning `java`. If user-influenced arguments like TLC configurations or module names contained shell metacharacters (e.g., `&`, `|`), they could be executed by the Windows command shell (`cmd.exe`).
**Learning:** `shell: true` is rarely necessary for well-known executables like `java` that don't rely on batch wrappers (`.bat` or `.cmd`). Relying on the shell for argument parsing introduces unnecessary and severe command injection risks.
**Prevention:** Always default to `shell: false` when using `spawn`. Only enable it if absolutely necessary (e.g., executing a `.bat` file on Windows), and in those cases, rigorously sanitize all inputs.

## 2025-03-27 - [Fix Command Injection Risk in npm spawn]
**Vulnerability:** The version string `latest` returned from `npm view` was validated using `!/^\d+\.\d+\.\d+/.test(latest)` in `src/update.ts`. Without an end-of-string anchor (`$`), a manipulated response containing valid semantic versioning followed by shell operators (e.g., `1.0.0 & echo Pwned`) could bypass the validation. When passed to `execFileAsync` calling `.cmd` on Windows (which requires `shell: true`), this allowed arbitrary command execution.
**Learning:** Due to Node.js security patches (mitigating CVE-2024-27980), spawning `.cmd` or `.bat` files requires `shell: true` to avoid an `EINVAL` error. This means `npm` execution on Windows natively runs through a shell. Therefore, you cannot mitigate injection simply by turning the shell off. You must strictly sanitize all inputs dynamically passed to the command.
**Prevention:** Always anchor regex validations (`^` and `$`) for command inputs to prevent trailing payload injection, especially when the executed command must run within a shell environment.
